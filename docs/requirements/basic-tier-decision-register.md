# Basic-tier Decision Register

## Status and authority

This register is the issue #62 consolidation point for the remaining Wits Quest Basic-tier product and governance decisions. It was prepared on 2026-08-13 by Kevin Ebrahim, Product and Player Experience Lead, for review by Caleb Pather, Cards, Game Systems and Quality Lead, and updated on 2026-08-14 in response to the PR #84 review. The update synchronises `BASIC-09` through `BASIC-12` with the confirmed decisions recorded in issues #71, #74, #77, and #63. It was updated again on 2026-08-21 to record the final email-verification decision and the approved broken-behaviour audit resolutions as `BASIC-17` through `BASIC-19`.

The labels used below are deliberate:

- **Confirmed** — supported by an approved decision record or an unambiguous current Gitea issue contract.
- **Blocked** — implementation must wait for the named owner to record the missing choice. A proposal elsewhere is not authority to invent the answer.
- **Deferred** — explicitly outside the Basic release.
- **Superseded** — an older statement conflicts with a newer or more authoritative decision and must not drive implementation.

The cited Gitea issue, comment, or approved Product decision is the evidence source. Approval of this register consolidates those sources; it does not retrospectively invent a stakeholder decision.

Team confirmation on 25 August 2026 affirms that the implemented five-question
challenge, score-based rewards with zero-to-two awarded cards, and current
move/Power-card CPU rules are intentional Wits World product decisions. This is
team approval of the current product; it is not evidence that the lecturer or
client formally amended wording in the supplied project brief. The team asked
about the supplementary Wits Quest brief mentioned there, but as of 25 August
2026 no supplementary brief had been provided to the team. It is therefore not
an additional source or a blocker for this dated review.

### BASIC-09 modifier amendment

The explicit BASIC-09/#74 amendment records the battle-ready Buff/Debuff contract: authored modifier targets are `hp`, `power`, or `damage_multiplier`; HP and Power use `add`; damage strength uses `multiply`; `effectValue` is the magnitude and is a percentage for damage strength; only damage-strength modifiers may define `durationTurns`; and missing required modifier metadata is invalid battle data. The catalogue, API, seed, and game-rules adapter must carry these fields rather than infer them. See [issue #74 comment 4832](https://sdp.ms.wits.ac.za/gradient-ascent/Wits-World/issues/74#issuecomment-4832).

### PvP timer-mode clarification

The `BASIC-10` one-minute PvP statement predates issue `#178` and refers only
to the deferred live PvP mode. The planned Intermediate asynchronous mode is a
separate polling-based contract with 24-hour decision windows and automatic
forfeiture. This clarification does not change the implemented Basic CPU timer
or timeout behavior. See the
[asynchronous PvP API contract](../architecture/asynchronous-pvp-api-contract.md).

### Reward-currency supersession

Issue `#193` and the confirmed progression rules supersede the coin-band clauses
in `BASIC-04` and the active coin references in `BASIC-12`. Permanent,
non-spendable points are the only active progression measure; challenge rewards
may still issue zero to two cards. Applied coin-schema history is preserved:
legacy wallets are read-only until account deletion, legacy ledger rows are
immutable, and new completion rows store zero in the compatibility column.

## Blocking decision requests

`BASIC-09` through `BASIC-12` are now confirmed in the cited issue comments.

`BASIC-17` through `BASIC-19` are also confirmed. `BASIC-17` requires an Auth0 tenant configuration change, not an application-authorisation change. `BASIC-18` is now enforced by migrations `0017` and `0018`. `BASIC-19` still requires reviewed content remediation before strict published-row enforcement can be completed.

Implementation update (2026-08-22): Mapbox GL JS with Mapbox Standard has
replaced the register's stale OpenFreeMap implementation note for `BASIC-13`.
Team clarification (2026-08-25): Mapbox is an allowed team-selected integration
under the project's broad implementation discretion. No separate explicit
client/lecturer approval by name is required or claimed; licensing/terms,
cost/usage ownership, token/CSP/privacy, deployed behaviour, and campus-data
evidence still remain. For `BASIC-19`, drafts now accept zero through four
moves, the API rejects a fifth, and publication requires exactly four. Migration
`0019_limit_creature_move_positions.sql` constrains stored move positions to one
through four; strict published-row enforcement remains
blocked by the 18 audited two-move definitions and must not fabricate content.

Issue #62 is closed. `BASIC-13` no longer has an unresolved product-selection
gate. Kevin still needs to record the Mapbox licensing/terms and cost/usage
owner, production token/CSP/privacy and deployed behaviour, and the decision and
provenance for any Wits-specific campus layer.

The account-deletion comment for #63 mentions transferring authored content to a system or Administrator account. Because `BASIC-11` confirms that Basic has no separate Administrator role, deletion handling must use the system-owned target; it must not introduce an Administrator role or an in-app role-management path.
